# FREITTY CS Operating System — ТЗ для Claude Code

## 1. Що це за проєкт

База знань відділу Customer Support (CS) компанії Freitty: політики, стандарти, процеси, процедури, інструкції, шаблони і реєстри. Freitty — американська компанія крос-докінгу і обробки вантажів; команда CS працює з України цілодобово і обслуговує клієнтів у США та Канаді.

Цей репозиторій — **єдине джерело правди** для бази знань CS. Сайт на Vercel — лише представлення для читання.

Мова змісту — українська. Системні назви (Freitty Hub, HubSpot, Dialpad, ClickUp, Notion, статуси ордерів, Order chat) — англійською, як у системах.

## 2. Архітектура документів (не змінювати без явної вказівки)

Архітектуру спроєктувала Head of Customer Support. Повна легенда — у `registry/legend.md`. Коротко:

| Код | Рівень | Що це |
|---|---|---|
| POL-NN | L1 Політика | Що дозволено і заборонено |
| STD-NN | L2 Стандарт | Вимірюваний поріг: час, відсоток, бал. **Усі числа живуть тільки тут** |
| PRC-N.0 | L2 Процес | Наскрізний потік від клієнта до результату |
| SOP-N.N | L3 Процедура | Як виконується один крок процесу |
| WI-NN | L4 Інструкція | Куди клікнути в системі |
| TPL-NN | L5 Шаблон | Готовий текст або форма |
| REG-NN | L5 Запис | Реєстр або журнал |

Потоки: 1.0 Contact-to-Resolution · 2.0 Lead-to-Order · 3.0 Order-to-Close · 4.0 Exception-to-Recovery · 5.0 Partner-to-Performance · 6.0 Hire-to-Certified · 7.0 Insight-to-Action · 8.0 Transport-Order-to-Close · E Допоміжні.

Пріоритети (Tier): 0 критичний · 1 операційний · 2 відкладений. Статуси: Чинний · Чернетка · Потребує оновлення · Не створено · Архів.

## 3. Правила (обов'язкові)

1. Кожен документ має **рівно одного власника** — людину, не команду.
2. Новий документ спершу отримує код у реєстрі, потім пишеться.
3. **Видалення заборонене.** Замість цього статус «Архів» і дата.
4. Зміст живе в одному місці. Документи посилаються один на одного кодом, а не копіюють текст.
5. **Числа (строки, відсотки, пороги) — тільки в STD.** SOP і POL посилаються на STD.
6. Посилання йдуть вниз за рівнями: SOP → STD, WI, TPL. Не навпаки.
7. Зміст документів **не вигадувати, не переписувати і не «покращувати»** без явної вказівки. Технічне форматування — можна.

## 4. Структура репозиторію

```

docs/<ТИП>/<КОД>-<slug>.md   документи бази (POL, STD, PRC, SOP, WI, TPL, REG)

```

### Шапка (frontmatter) кожного документа в `docs/`

```yaml
---
code: SOP-1.7
title: Пропущені дзвінки і зворотний виклик
level: L3 Процедура
stream: 1.0 Звернення
tier: 0 - критичний
owner: Oksana
status: Чернетка
version: "0.1"
approved: null
next_review: null
related: [STD-19, SOP-1.6, SOP-1.1]
source: notion | design-2026-10
---
```

**Після імпорту реєстр генерується з frontmatter** (`scripts/build-registry`). `registry/registry.yaml` — лише стартове значення і перевірка розбіжностей.

## 5. Сайт (VitePress)

| Сторінка | Що показує |
|---|---|
| **Головна = навігатор «Що робити, коли…»** | 20–30 робочих ситуацій оператора (пропущений дзвінок, клієнт питає статус, підозра на hazmat, водій без BOL, кінець зміни, відключення світла…) → посилання на документ. Ситуації взяти з SOP і TPL; якщо не впевнений — позначити «перевірити» |
| **Реєстр** | Таблиця всіх документів з фільтрами: тип, потік, Tier, статус, власник. Значки статусів |
| **Ядро v1** | Документи з `core.yaml` і їхній стан |
| **Готовність бази** | Лічильники як в аркуші «Зведення»: усього, за статусом, за Tier, «критичні не створені», «без власника», % чинних |
| **Потоки** | Сторінка на кожен потік 1.0–8.0, E: процес PRC і його SOP |
| **Журнал рішень** | `decisions/decisions.md` |
| **Таймінги** | Шпаргалка всіх часових норм з посиланням на STD-джерело кожного числа. Таблиця генерується зі STD, а не пишеться окремо |
| **Документ** | Шапка (код, власник, статус, версія, перегляд), зміст, блок «Пов'язані» (за `related`), «Оновлено» з git |

Технічні вимоги:
- Бічне меню за типами і потоками; вбудований локальний пошук (**перевірити, що шукає кирилицею**).
- Діаграми Mermaid.
- Без бекенду, бази даних, аналітики, трекерів, зовнішніх шрифтів із CDN, якщо можна без них.
- Світла і темна теми.

## 6. Доступ і дані

- **Сайт не може бути публічним.** Захист доступу на Vercel (Deployment Protection) або middleware з паролем — обери і задокументуй у README. До увімкнення захисту посилання нікому не передається.
- **Жодних персональних даних клієнтів** (імена, телефони, email).
- **Жодних поіменних показників операторів** на сайті. В `analytics/` — тільки агреговані дані.

## 7. Перевірки (`npm run check`)

- кожен файл у `docs/` має повний frontmatter;
- код унікальний і відповідає формату;
- усі коди в `related` існують;
- власник — одна людина (рядки з «/» або «Уточнити» → попередження);
- биті внутрішні посилання;
- розбіжності frontmatter ↔ `registry/registry.yaml` → у звіт, не виправляти мовчки.

## 8. Чого не робити

- Не змінювати архітектуру кодів, назви потоків, статуси.
- Не зливати `proposals/` у документи без явної команди.
- Не видаляти документи і не перенумеровувати коди.
- Не публікувати сайт без захисту доступу.
